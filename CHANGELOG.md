## [Unreleased]

### Added

- **Supabase Foundation** (`feature/supabase-foundation`, infrastructure only at the time this phase shipped — Leads became the first business module to read/write live Supabase in a later phase, see below):
  - Typed environment layer (`lib/env.ts`, `.env.example`): `NEXT_PUBLIC_DATA_MODE` (`mock` default / `supabase`), `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Reading env never throws in mock mode; `SupabaseConfigurationError` is thrown only when `supabase` mode is explicitly selected without both credentials present
  - Supabase client factories using the current `@supabase/ssr` pattern (`lib/supabase/client.ts` for Client Components, `lib/supabase/server.ts` for Server Components/Actions, `lib/supabase/middleware.ts` session-refresh helper) — no deprecated `@supabase/auth-helpers-*`, no service-role client anywhere in the app, no module-scoped singleton client
  - Auth foundation (`lib/auth/session.ts`, `lib/auth/actions.ts`): sign in/out, session/current-user retrieval, password reset request/update, all normalized through `normalizeSupabaseError`; minimal (intentionally not final) pages at `/sign-in`, `/reset-password`, `/update-password`, and an auth callback route handler (`src/app/auth/callback/route.ts`) for the password-reset PKCE flow
  - Workspace membership data model: `profiles`/`workspaces`/`workspace_members` domain types (`src/types/`), `WorkspaceMemberRole` (`owner`/`admin`/`manager`/`team`/`viewer`) and `WorkspaceMemberStatus` (`active`/`invited`/`suspended`) enums, and pure TS mirrors of the SQL role-check functions (`lib/auth/workspaceRoles.ts`)
  - 8 ordered SQL migrations under `supabase/migrations/`: extensions, `profiles` (+ `handle_new_user()` auto-provisioning trigger on `auth.users`), `workspaces`, `workspace_members` (unique on `workspace_id`+`user_id`), a shared `set_updated_at()` trigger, `is_workspace_member()`/`has_workspace_role()`/`current_user_workspace_ids()` RLS helper functions (`security definer`, pinned `search_path`), RLS enablement + policies on all three tables (every policy scoped `to authenticated`, none use a bare `using (true)`), and private Storage buckets (`documents`, `avatars`, both `public = false`) with path-scoped object policies
  - Centralized data-provider selection point (`lib/data/provider.ts`, `selectRepository()`) — the single place any future module's `NEXT_PUBLIC_DATA_MODE` branching happens; `lib/data/index.ts` remains the unconditional implementation for every business module (Leads/Clients/Events/Contracts/Finance/Documents) this phase
  - Route protection middleware (`src/middleware.ts`) built around a pure, fully unit-tested decision function (`lib/middleware/routeProtection.ts`) — activates only when `NEXT_PUBLIC_DATA_MODE=supabase`; mock mode (the default) never requires a login and never constructs a Supabase client
  - Hand-authored placeholder `src/types/database.types.ts` (Supabase-`gen types`-shaped; regenerate via `npm run supabase:types` once a project is linked) and a DB-row-to-domain-type mapping boundary (`lib/supabase/mappers.ts`)
  - `core/errors` extended with `UnauthorizedError`/`ForbiddenError`/`NetworkError`/`UnknownError` alongside the existing `NotFoundError`/`ValidationError`/`ConflictError`; `lib/supabase/errors.ts` normalizes Supabase Auth/PostgREST/Postgres errors into this taxonomy so raw database internals never reach the UI
  - `npm run supabase:*` scripts (`init`/`start`/`stop`/`reset`/`migration:new`/`migration:up`/`link`/`push`/`types`), all `npx`-based — nothing installed globally
  - 114 new tests (9 new files) covering environment validation, provider selection, error normalization, DB-row mapping, auth/session helpers (mocked Supabase client), Workspace role helpers, middleware redirect decisions, and migration file structure/ordering/content — none require a live Supabase connection
- **Leads migrated to Supabase (first business-module migration):**
  - 5 further SQL migrations under `supabase/migrations/`: `leads` (UUID PK, `workspace_id` FK, 9-value status `CHECK`, soft delete via `status = 'archived'` + `archived_at`, no restore/delete path — matching the mock's existing terminal-status model exactly), `notes` and `timeline_activities` (polymorphic `owner_type`/`owner_id` tables reused by every future owner type, `owner_type` `CHECK`-constrained to `'lead'` only this phase), shared `updated_at` triggers on `leads`/`notes`, and RLS enablement (Workspace isolation only via `is_workspace_member()` — no owner/admin role gating, unlike `workspaces`/`workspace_members`)
  - `LeadsRepository` interface (`lib/data/leads/repository.ts`) implemented once by the (refactored, behavior-unchanged) mock repository and once by a new Supabase repository, selected via `lib/data/provider.ts`'s `selectRepository()` inside `lib/data/index.ts`'s thin wrapper functions — no UI file branches on data mode, and the public function signatures (`getLeads`, `getLeadById`, `createLead`, `updateLead`, `updateLeadStatus`, `archiveLead`, `markWelcomeGuideSent`, notes/timeline getters) are unchanged
  - The Supabase Leads repository uses the **browser** Supabase client (`lib/supabase/client.ts`), not the server one — the Leads UI fetches from Client Components, and the server client's `server-only`/`next/headers` dependency cannot be imported into a client bundle. `lib/auth/workspaceSessionClient.ts` is a Client-Component-safe twin of `lib/auth/workspaceSession.ts` for this reason (same resolution logic and result shape, browser client instead of server client)
  - Search matches the mock's substring-over-`"${first_name} ${last_name} ${email}"` semantics exactly (applied in application code, not pushed into SQL as independent per-column `ILIKE` filters, which would miss a combined "first last" query); other filters (status/source/eventType/includeArchived) are pushed into the Supabase query
  - Known, documented Phase 1 gaps: `restoreLead`/`deleteLead` were not added (the mock has no restore path — "archived" is terminal, like "converted" — and the public repository interface intentionally was not expanded); Lead → Client conversion (`LeadConversionService`) remains entirely mock-only regardless of data mode, since it also reads/writes the not-yet-migrated Clients store; the shared `togglePinNote` (used by 8 modules) also remains mock-only, so pinning a Supabase-backed Lead note is not yet wired up
  - 54 new tests (3 new files) covering the Supabase repository (CRUD, search, filters, soft delete/archive, timeline, notes, Workspace scoping, error normalization), the client-safe workspace-session resolver, and the 5 new migrations' structure/RLS/constraints

  - Schema validated against every requested future capability (drag-and-drop uploads, multiple attachments per record, folder organization, file/image/video/PDF previews, bulk uploads, file version history, soft delete, storage quotas, AI indexing/search) — none require redesigning `media_assets`; each is either already supported today or a purely additive future column/table, documented in `docs/database.md`'s "Future extensions" list
