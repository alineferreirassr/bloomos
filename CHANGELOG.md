# Changelog

All notable changes to BloomOS are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- Initial repository documentation: `README.md`, `CLAUDE.md`, `BLOOMOS_BIBLE.md`, `ROADMAP.md`, `TODO.md`, `CHANGELOG.md`
- `docs/` specs: `database.md`, `workflows.md`, `ui.md`, `automations.md`, `integrations.md`, `permissions.md`, `ai.md`, `design-system.md`
- Project initialized as a standalone repository (no external handoff package; BloomOS is being built from scratch)
- Full technical architecture proposed and approved: folder structure, module boundaries, data layer, auth/authorization strategy, Supabase integration plan, routing, shared components, state management, validation, error handling, file/document storage, testing strategy, security considerations, and Sprint 1 implementation order
- `PRODUCT_PRINCIPLES.md` — long-term product philosophy (workflows over screens, automation before manual work, AI assists but never replaces business approval, build for long-term scalability)
- Workspace concept documented (`BLOOMOS_BIBLE.md` §7) as the future multi-tenant boundary; not implemented in the MVP
- Next.js 16 (App Router) + TypeScript (strict) + Tailwind CSS v4 + ESLint project scaffolded
- Design tokens defined in `src/app/globals.css` (provisional neutral palette + accent — recorded in `docs/design-system.md`)
- Approved folder structure created: `app/`, `modules/`, `components/`, `lib/`, `config/`, plus reserved placeholders `core/`, `services/`, `features/`, `automation/`, `audit/`, `email/` (each with a README noting it's a placeholder, per the approved architecture)
- Shared UI primitives: `Button`, `Card`, hand-rolled nav icon set (no icon library dependency)
- `AppShell`, `Sidebar`, `TopBar`, and responsive `MobileNav` (drawer on mobile, breakpoint at `md`)
- Minimal Dashboard shell (`/dashboard`) with placeholder metric cards (Leads, Clients, Events, Contracts, Finance) over mock data, ready to go live as each module ships
- `docs/database.md` gains a provisional `file_path` note on `contracts` for future document storage
- **Leads module, end to end (mock data):** list (search, status/source/event-type filters, archive visibility, responsive table + cards, empty/loading/error states), detail (contact/event info, pinned + all notes, timeline, status selector, next-recommended-action), create/edit forms (zod + react-hook-form, client-side and authoritative data-layer validation), Notes (categories/priorities, pinning), Welcome Guide mock action, Archive, and Convert-to-Client (confirmation modal, duplicate-conversion prevention, history preservation)
- `LeadConversionService` (`modules/leads/services/`) — owns the Lead → Client conversion business rule; UI only ever calls it via `lib/data`
- `core/workflows/leadWorkflow.ts` — the canonical Lead lifecycle (`canTransition`, `getNextStatuses`, `isTerminalStatus`, `getNextRecommendedAction`), the single source of truth consumed by both the data layer and the UI
- Centralized timeline recording (`recordTimelineActivity` in `lib/data/mock/timelineStore.ts`) — no module constructs a timeline entry by hand
- `lib/data/index.ts` — the swappable mock data-access layer (Leads, Notes, Timeline, minimal Clients, Dashboard metrics), with typed `DataResult` success/failure handling
- Minimal Client proof page (`/clients/[id]`) — just enough to demonstrate the conversion workflow; the full Clients module is still future work
- Vitest + React Testing Library test suite: zod schemas, lifecycle transitions, CRUD operations, conversion (including duplicate-prevention and history-preservation), notes/pinning, list filtering, and responsive list rendering
- Dashboard's Leads/Clients metrics now read live counts from the data layer instead of static placeholders
- **Clients module foundation (mock data — types, enums, schemas, data layer; UI not yet built):** full canonical `Client` model (contact info, address, tags, `internal_status`, couple information, important operational details, VIP flag) in `src/types/client.ts`; `core/enums/clientStatus.ts` (`active`/`planning`/`past_client`/`inactive`/`archived`), `core/enums/contactMethod.ts`, and `core/enums/entityType.ts`; `modules/clients/schema.ts` (zod form + authoritative data schemas), `mappers.ts`, `constants.ts`, `testUtils.ts`; `core/workflows/clientWorkflow.ts` — deterministic recommended-next-action helper; full Client CRUD, filtering, and dedicated tags/VIP/communication-preference/archive/restore mutations in `lib/data/index.ts`, each recording its own timeline entry
- **Notes and Timeline generalized to a shared owner_type/owner_id shape** (`lead` or `client`) instead of Lead-only tables, so Client notes and Client timeline entries reuse the same architecture and `recordTimelineActivity` mechanism as Leads rather than duplicating it; `NOTE_CATEGORIES` and `TIMELINE_ACTIVITY_TYPES` expanded with Client-relevant values (`relationship_detail`, `accessibility`, `dietary_restriction`, `communication`; `client_created`, `client_updated`, `tags_changed`, `vip_status_changed`, `communication_preference_changed`, `client_archived`, `client_restored`)
- Dashboard now reports Total/Active/VIP/Archived Client counts (alongside Leads) from the Clients data layer
- **Workspace isolation added to shared Notes and Timeline:** `Note` and `TimelineActivity` both gain `workspace_id`; every notes/timeline read and write in `lib/data/index.ts` now scopes by `workspace_id` together with `owner_type`/`owner_id` (never `owner_id` alone), deriving `workspace_id` from the owning Lead/Client record rather than assuming a single tenant; `recordTimelineActivity()` takes `workspaceId` as its first parameter; documented in `docs/database.md` that a polymorphic `owner_id` can't carry a normal foreign key to two different tables, so ownership and workspace consistency must be validated in the data layer now and by Supabase RLS once connected
- **Notes UI generalized and relocated:** `NoteCard`, `NoteForm`, `NoteCategoryBadge`, `NotePriorityBadge`, and `NotesSection` moved from `modules/leads/components/` to `modules/notes/components/`; `NotesSection`'s contract changed from a Lead-only `leadId` prop to a generic `workspaceId`/`ownerType`/`ownerId`/`notes`/`onCreateNote`/`onTogglePin`/`readOnly` contract, with the actual mutation injected by the caller instead of the component importing `@/lib/data` itself — Lead and future Client screens compose the same implementation with no duplicated UI or business logic
- **Timeline rendering generalized and relocated:** `LeadTimeline` renamed to `Timeline` and moved from `modules/leads/components/` to `modules/timeline/components/`; unchanged behavior, now explicitly generic (`TimelineActivity[]`, no owner-specific logic)
- Lead → Client conversion validated against the full expanded Client model: new tests confirm the produced Client has no undefined required fields and matches the canonical 44-field shape, `workspace_id` and `originating_lead_id` are preserved from the Lead, and the Lead's and new Client's timelines remain correctly and separately scoped (no cross-contamination)
- **Clients module UI, end to end (mock data), built entirely on the approved foundation with no further architecture changes:** list (`/clients` — search across name/email/phone/partner, status/source/tag/VIP filters, archived toggle, responsive table + cards with Name/Partner/Email/Phone/Status/VIP/Tags/Source/Created/Next Action columns, empty/loading/error states); full profile (`/clients/[id]` — header with avatar initials, status/VIP badges, and quick actions; Contact, Relationship, Address, Preferences, and Internal sections; shared `NotesSection` and `Timeline`); create/edit forms (`/clients/new`, `/clients/[id]/edit`) reusing `clientFormSchema` with `useFieldArray` for important dates, dirty-state protection, and the same cancel/validation pattern as `LeadForm`
- Client quick actions with optimistic updates and rollback on failure: `VipToggle`, `ClientStatusSelect` (excludes `archived` — only reachable via the dedicated Archive action, keeping `internal_status` and `archived_at` in sync), `ContactMethodSelect`, composed into `ClientActions` (Edit, Archive/Restore, VIP, Status, Contact method — no delete)
- Component/interaction test coverage for the new UI: list rendering, filter interactions, form validation and submission, VIP toggle (including rollback), archive, restore, tags editing (including rollback), and a profile-page smoke test
- `TagsEditor` (`modules/clients/components/`) — quick-action for adding/removing Client tags, calling the existing `updateClientTags` (which already recorded its own `tags_changed` timeline entry but had no UI surface until now); same optimistic-update-with-rollback pattern as `VipToggle`/`ContactMethodSelect`; renders as a static comma-separated list instead of the editor when the Client is archived
- Browser smoke test performed against a running dev server, covering the full Client lifecycle in one continuous session (verified via client-side navigation only, since a hard page reload intentionally resets the mock store): add + pin a note, edit the profile (preferences, important dates), change status, change preferred contact method, toggle VIP both directions, add/remove tags, archive (confirmed quick actions and tags become read-only, Notes remain editable by design), restore, confirmed Dashboard metrics update live, confirmed mobile rendering of the list/profile/create-form, and confirmed Lead → Client conversion opens the correct new Client's profile

### Fixed

- Navigation no longer leads to 404s: `/leads`, `/clients`, `/events`, `/contracts`, `/finance` each render a shared `ComingSoon` placeholder until their module is built, so every nav link and Dashboard metric card resolves to a real page
- `LeadDetailView`'s refetch-after-mutation no longer flashes a full loading skeleton, which was unmounting `LeadActions` before its success/error feedback (e.g. "Welcome Guide marked as sent.") ever became visible — found via browser smoke testing

### Changed

- Renamed the tenancy concept from "organization" to **Workspace** throughout `docs/database.md`, `docs/permissions.md`, and `docs/ai.md` (`organization_id` → `workspace_id`, `organizations` table → `workspaces` table)
- `docs/database.md` and `docs/workflows.md`: `lead_notes`/`lead_timeline_activities` tables replaced by polymorphic `notes`/`timeline_activities` tables (`owner_type` + `owner_id`); `clients.origin_lead_id` renamed to `originating_lead_id`; `clients` table schema expanded to the full canonical Client model
- `ROADMAP.md`: Dashboard moved earlier in the Phase 1 sequence (built as a shell alongside the app frame, then wired up incrementally as each module ships, instead of being built last); added Notifications (Phase 3) and Global Search (Phase 4) to future modules; Phase 0 now includes scaffolding reserved structural folders (`core/`, `services/`, `features/`, `automation/`, `audit/`, `email/`) as placeholders ahead of their implementation phase
- `clientFormSchema`: removed `.default()` on `important_dates`/`do_not_call`/`surprise_event_confidentiality` — with zod + `zodResolver`, a field-level default desyncs the resolver's input/output types from react-hook-form's `TFieldValues`, which `tsc` caught when `ClientForm` was built; `ClientForm`'s explicit `emptyDefaults` already supplies the same values, so behavior is unchanged
- **Design-system correction pass (on `feature/design-system`), reproducing the actual approved handoff (`bloomos-handoff/`, Classical design system) instead of a prior from-scratch redesign attempt:** every token in `globals.css` recopied verbatim from `_ds/classical-.../styles.css` — colors (`#f3f2f2` background, `#eae9e9` sidebar/dialog surface, `#b68235` accent, `color-mix()`-based border/muted-text), body face switched from Inter to **Lora** (the approved file's actual body font, overriding earlier in-chat prose that said Inter), radii corrected from 12–16px down to the approved 2/4/7px scale, shadows removed from cards entirely (`.card` has no fill and no shadow in the approved system — only a border), buttons changed from filled to **outline** style; `Badge` gained an `outline` tone and `LeadStatusBadge`/`ClientStatusBadge` tone lookups were corrected to the approved 3-tone system (outline/accent/neutral, no separate success/warning/danger palette); Lucide icon choices corrected (Leads = `Users`, Clients = `User`, previously swapped); card section headers (`Contact`, `Notes`, etc.) corrected to 17px serif per `.card-title`, not small muted sans labels; documented in `docs/design-system.md` along with 5 disclosed, deliberate remaining differences from the reference mockups (Header action-button placement, Dashboard recent-leads/tasks panels, KPI note line, sidebar item count, all of which would require restructuring page composition or the data layer to close, both out of scope for a presentation-only pass)
