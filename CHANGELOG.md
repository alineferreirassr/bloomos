## [Unreleased]

### Added

- **Supabase Foundation** (`feature/supabase-foundation`, infrastructure only at the time this phase shipped — Leads became the first business module to read/write live Supabase in a later phase, see below):
  - Typed environment layer (`lib/env.ts`, `.env.example`): `NEXT_PUBLIC_DATA_MODE` (`mock` default / `supabase`), `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Reading env never throws in mock mode; `SupabaseConfigurationError` is thrown only when `supabase` mode is explicitly selected without both credentials present
  - Supabase client factories using the current `@supabase/ssr` pattern (`lib/supabase/client.ts` for Client Components, `lib/supabase/server.ts` for Server Components/Actions, `lib/supabase/middleware.ts` session-refresh helper) — no deprecated `@supabase/auth-helpers-*`, no service-role client anywhere in the app, no module-scoped singleton client
  - Auth foundation (`lib/auth/session.ts`, `lib/auth/actions.ts`): sign in/out, session/current-user retrieval, password reset request/update, all normalized through `normalizeSupabaseError`; minimal (intentionally not final) pages at `/sign-in`, `/reset-password`, `/update-password`, and an auth callback route handler (`src/app/auth/callback/route.ts`) for the password-reset PKCE flow
  - Workspace membership data model: `profiles`/`workspaces`/`workspace_members` domain types (`src/types/`), `WorkspaceMemberRole` (`owner`/`admin`/`manager`/`team`/`viewer`) and `WorkspaceMemberStatus` (`active`/`invited`/`suspended`) enums, and pure TS mirrors of the SQL role-check functions (`lib/auth/workspaceRoles.ts`)
  - 8 ordered SQL migrations under `supabase/migrations/`: extensions, `profiles` (+ `handle_new_user()` auto-provisioning trigger on `auth.users`), `workspaces`, `workspace_members` (unique on `workspace_id`+`user_id`), a shared `set_updated_at()` trigger, `is_workspace_member()`/`has_workspace_role()`/`current_user_workspace_ids()` RLS helper functions (`security definer`, pinned `search_path`), RLS enablement + policies on all three tables (every policy scoped `to authenticated`, none use a bare `using (true)`), and private Storage buckets (`documents`, `avatars`, both `public = false`) with path-scoped object policies
  - Centralized data-provider selection point (`lib/data/provider.ts`, `selectRepository()`) — the single place any future module's `NEXT_PUBLIC_DATA_MODE` branching happens; `lib/data/index.ts` remains the unconditional implementation for every business module (Leads/Clients/Events/Contracts/Finance/Documents) this phase
  - Route protection middleware (`src/middleware.ts`) built around a pure, fully unit-tested decision function (`lib/middleware/routeProtection.ts`) — activates only when `NEXT_PUBLIC_DATA_MODE=supabase`; mock mode (the default) never requires a login and never constructs a Supabase client
  - Hand-authored placeholder `src/types/database.types.ts` (Supabase-`gen types`-shaped; regenerate via `npm run supabase:types` once a project is linked) and a DB-row-to-domain-type mapping boundary (`lib/supabase/mappers.ts`)
  - `core/errors` extended with `UnauthorizedError`/`ForbiddenError`/`NetworkError`/`UnknownError` alongside the existing `NotFoundError`/`ValidationError`/`ConflictError`; `lib/supabase/errors.ts` normalizes Supabase Auth/PostgREST/Postgres errors into this taxonomy so raw database internals never reach the UI
  - `npm run supabase:*` scripts (`init`/`start`/`stop`/`reset`/`migration:new`/`migration:up`/`link`/`push`/`types`), all `npx`-based — nothing installed globally
  - 114 new tests (9 new files) covering environment validation, provider selection, error normalization, DB-row mapping, auth/session helpers (mocked Supabase client), Workspace role helpers, middleware redirect decisions, and migration file structure/ordering/content — none require a live Supabase connection
- **Leads migrated to Supabase (first business-module migration):**
  - 5 further SQL migrations under `supabase/migrations/`: `leads` (UUID PK, `workspace_id` FK, 9-value status `CHECK`, soft delete via `status = 'archived'` + `archived_at`, no restore/delete path — matching the mock's existing terminal-status model exactly), `notes` and `timeline_activities` (polymorphic `owner_type`/`owner_id` tables reused by every future owner type, `owner_type` `CHECK`-constrained to `'lead'` only this phase), shared `updated_at` triggers on `leads`/`notes`, and RLS enablement (Workspace isolation only via `is_workspace_member()` — no owner/admin role gating, unlike `workspaces`/`workspace_members`)
  - `LeadsRepository` interface (`lib/data/leads/repository.ts`) implemented once by the (refactored, behavior-unchanged) mock repository and once by a new Supabase repository, selected via `lib/data/provider.ts`'s `selectRepository()` inside `lib/data/index.ts`'s thin wrapper functions — no UI file branches on data mode, and the public function signatures (`getLeads`, `getLeadById`, `createLead`, `updateLead`, `updateLeadStatus`, `archiveLead`, `markWelcomeGuideSent`, notes/timeline getters) are unchanged
  - The Supabase Leads repository uses the **browser** Supabase client (`lib/supabase/client.ts`), not the server one — the Leads UI fetches from Client Components, and the server client's `server-only`/`next/headers` dependency cannot be imported into a client bundle. `lib/auth/workspaceSessionClient.ts` is a Client-Component-safe twin of `lib/auth/workspaceSession.ts` for this reason (same resolution logic and result shape, browser client instead of server client)
  - Search matches the mock's substring-over-`"${first_name} ${last_name} ${email}"` semantics exactly (applied in application code, not pushed into SQL as independent per-column `ILIKE` filters, which would miss a combined "first last" query); other filters (status/source/eventType/includeArchived) are pushed into the Supabase query
  - Known, documented Phase 1 gaps: `restoreLead`/`deleteLead` were not added (the mock has no restore path — "archived" is terminal, like "converted" — and the public repository interface intentionally was not expanded); Lead → Client conversion (`LeadConversionService`) remains entirely mock-only regardless of data mode, since it also reads/writes the not-yet-migrated Clients store; the shared `togglePinNote` (used by 8 modules) also remains mock-only, so pinning a Supabase-backed Lead note is not yet wired up
  - 54 new tests (3 new files) covering the Supabase repository (CRUD, search, filters, soft delete/archive, timeline, notes, Workspace scoping, error normalization), the client-safe workspace-session resolver, and the 5 new migrations' structure/RLS/constraints
- **Clients migrated to Supabase (second business-module migration), plus atomic Lead → Client conversion:**
  - 6 further SQL migrations under `supabase/migrations/`: `clients` (UUID PK, `workspace_id` FK, nullable `originating_lead_id` FK → `leads`, 5-value `internal_status` `CHECK`, soft delete via `internal_status = 'archived'` + `archived_at` — unlike Leads, reversible via `restoreClient`), widening the existing shared `notes`/`timeline_activities` tables' `owner_type` `CHECK` to add `'client'` and `timeline_activities.type` `CHECK` to add `lead_converted` and the 7 Client activity types, a shared `updated_at` trigger on `clients`, RLS enablement (Workspace isolation only via `is_workspace_member()`, matching Leads — no delete policy), indexes (`workspace_id`, `workspace_id`+`internal_status`, `workspace_id`+`created_at desc`, a partial VIP index, a `tags` GIN index, `originating_lead_id`), and Lead → Client conversion support (a real FK from `leads.converted_client_id` → `clients.id`, a `UNIQUE` constraint on `clients.originating_lead_id`, and the `convert_lead_to_client(uuid, text)` function)
  - `ClientsRepository` interface (`lib/data/clients/repository.ts`) implemented once by a mock repository (extracted verbatim from the prior mock logic) and once by a new Supabase repository, same `selectRepository()` pattern as Leads — public function signatures unchanged (`getClients`, `getClientById`, `createClient`, `updateClient`, `updateClientStatus`, `updateClientTags`, `setClientVipStatus`, `updateClientContactPreference`, `archiveClient`, `restoreClient`, `getClientNextAction`, notes/timeline getters). The shared `togglePinNote` dispatcher (`lib/data/index.ts`) now tries `leadsRepository()` then `clientsRepository()` before falling through to the generic mock-only path for every other owner type.
  - **Lead → Client conversion goes live in `supabase` mode**, via a new `ConversionRepository` pair (`lib/data/conversion/`) spanning both domains: mock delegates unchanged to `LeadConversionService` (left untouched); Supabase calls the `convert_lead_to_client` Postgres function through `supabase.rpc(...)` — `security invoker` (not `security definer`, so RLS still governs every statement), `select ... for update` row-locking making duplicate-conversion prevention atomic rather than a check-then-act race, and a single implicit transaction so a rejected conversion (Lead not found, already converted, or **archived** — new in this phase, the mock version never rejected archived Leads) never leaves a half-created Client or partially-updated Lead behind. Field-copy semantics mirror `LeadConversionService` exactly; no Event is created.
  - Dashboard Client metrics (Total/Active/VIP/Archived) now read live Supabase data in `supabase` mode with no Dashboard code changes — they already called `getClients()`, which is now repository-routed.
  - Known, documented limitation: Events/Contracts/Finance/Documents (all still mock-only) continue reading the mock Clients store directly (`readClients()`) for cross-references (e.g. an Event's Client name) regardless of data mode — they'll see the mock store's seeded Clients even in `supabase` mode until each of those modules gets its own migration phase.
  - 41 new tests (2 new files: 34 for the Clients Supabase repository, 7 for the conversion Supabase repository) covering Clients CRUD/filters/status/tags/VIP/contact-preference/archive-restore/notes/pin-unpin/timeline/Workspace-isolation, and conversion (success, archived-Lead rejection, already-converted rejection, not-found, cross-Workspace-via-RLS, non-business-rule error normalization); the existing migration-file-count assertion updated from 13 to 19

Public function signatures unchanged (`getEvents`, `getEventById`, `createEvent`, `updateEvent`, `updateEventStatus`, `updateEventLifecycleStage`, `updateEventPriority`, `archiveEvent`, `restoreEvent`, `cancelEvent`, `completeEvent`, `getEventNextAction`, `getChecklistByEventId`, `createChecklistItem`, `updateChecklistItem`, `updateChecklistItemStatus`, `completeChecklistItem`, `deleteChecklistItem`, `reorderChecklistItems`, `getScheduleByEventId`, `createScheduleItem`, `updateScheduleItem`, `updateScheduleItemStatus`, `deleteScheduleItem`, `reorderScheduleItems`, `getNotesByEventId`, `createEventNote`, `getTimelineByEventId`).   - Dashboard Event metrics (Upcoming/This Week/Today/Tomorrow/Weekend/Awaiting Contract/Awaiting Deposit/In Planning/Ready/Completed This Month/Critical/Overdue Checklist Items/Checklist Completion %) now read live Supabase data in `supabase` mode with no Dashboard code changes — `getDashboardMetrics()`'s checklist computation was changed from a direct mock-store read to `Promise.all`-ing `getChecklistByEventId()` per Event (the same repository-routed function every other caller already uses) rather than adding a new, spec-external repository method.

- **Shared Media Library foundation (infrastructure only — no UI, no module migrated onto it yet):**
  - New, generic, polymorphic `media_assets` table (`supabase/migrations/20260719100000_media_assets.sql`) — pure storage-object metadata (original/stored filename, storage bucket/path, MIME type, extension, file size, checksum, width/height/duration, version, `uploaded_by`) with **no business-specific fields** (no category, folder, visibility, or workflow status). Deliberately independent of the existing mock-only `documents` table/module — nothing here imports from or modifies `lib/documentFile.ts`, `modules/documents/*`, or any Documents mock code. `owner_type` `CHECK`-constrained to `lead`/`client`/`event` this phase (the only owner types with a live Supabase table), following the exact incremental-widening discipline already established for `notes`/`timeline_activities`/`checklist_items`; `document`, `contract`, `invoice`, `payment`, `expense`, `team_kb_article`, `client_kb_article`, `notification`, and `automation` are captured as the full planned owner-type set (`src/lib/media/ownerTypes.ts`) for every future module to attach through, without needing any repository or service code change when each is eventually widened in
  - 5 further SQL migrations: a dedicated private `media-assets` Storage bucket + `storage.objects` policies (deliberately not the existing `documents` bucket, to keep the Media Library fully independent), a shared `updated_at` trigger, indexes (`workspace_id`+`owner_type`+`owner_id`, `workspace_id`+`archived_at`, and a uniqueness guard on `storage_bucket`+`storage_path`), RLS enablement (Workspace isolation only via `is_workspace_member()`, no delete policy — soft delete only via `archived_at`, reversible via `restoreMediaAsset`), and widening `timeline_activities.type`'s `CHECK` to add 4 new media-asset activity types (`owner_type` needed no widening — media-asset activity is always logged against the owning Lead/Client/Event, never against the asset itself)
  - `MediaAssetsRepository` interface (`lib/data/media/repository.ts`) — `getMediaAssetById`, `getMediaAssetsByOwner`, `uploadMediaAsset`, `replaceMediaAssetVersion`, `downloadMediaAsset`, `getMediaAssetDownloadUrl`, `verifyMediaAssetChecksum`, `deleteMediaAsset`, `restoreMediaAsset` — implemented once as a mock repository and once as a Supabase repository, selected via the same `selectRepository()` pattern as Leads/Clients/Events, wired into `lib/data/index.ts` with the same thin-wrapper convention
  - Real SHA-256 checksums (`src/lib/media/checksum.ts`, Web Crypto `crypto.subtle`) computed over actual file bytes in both mock and Supabase mode — an upgrade over the Documents module's older placeholder hash of just the file name and size. `verifyMediaAssetChecksum` re-downloads and recomputes to detect drift
  - **Versioning is in-place**, not a row chain: `replaceMediaAssetVersion` updates the same row's `version`/checksum/size/MIME type rather than inserting a new row, while the storage path embeds the version segment (`.../v{version}/{stored_filename}`) so a prior version's bytes are never overwritten in Storage even though only the latest metadata row is kept
  - MIME/extension/file-size validation (`src/lib/media/mediaFile.ts`, broad category-based size limits — image/video/audio/document/archive/other — independent of Documents' own allowlist) and image-dimension-detection/image-optimization hooks (`src/lib/media/imageMetadata.ts`) that fail soft (no image-processing library is installed; optimization is an explicit no-op passthrough reserved for future wiring)
  - Every upload/replace/archive/restore logs a Timeline entry against the media asset's **owning entity** (never against the asset itself), reusing the existing `insertTimelineActivity`/`recordTimelineActivity` mechanism — no new Timeline infrastructure, and a durable audit trail a future dedicated version-history table could be backfilled from
  - Schema validated against every requested future capability (drag-and-drop uploads, multiple attachments per record, folder organization, file/image/video/PDF previews, bulk uploads, file version history, soft delete, storage quotas, AI indexing/search) — none require redesigning `media_assets`; each is either already supported today or a purely additive future column/table, documented in `docs/database.md`'s "Future extensions" list
  - Mock mode keeps real file bytes in an in-memory `Map` alongside the metadata store (both reset together), unlike Documents' metadata-only mock — `downloadMediaAsset`/`verifyMediaAssetChecksum` are genuinely functional in mock mode, not simulated
  - 43 new tests (3 new files: `mediaFile.test.ts`, and the media mock/Supabase repositories) covering file validation/path/checksum helpers, upload/replace-version/download/signed-URL/checksum-verification/archive/restore in both mock and Supabase mode, owner-type rejection, and Workspace scoping; the migration-file-count assertion updated from 27 to 33

  - 8 further SQL migrations under `supabase/migrations/`: `contract_templates` (created before `contracts` since `contracts.template_id` references it; read-only in this phase — RLS grants select only, no seeded rows), `contracts` (UUID PK, `workspace_id` FK, `client_id` FK → `clients` — **required**, `event_id` nullable FK → `events`, `template_id` nullable FK → `contract_templates`, independent `status`/`signature_status` `CHECK`s mirroring `core/workflows/contractWorkflow.ts`, `version_history` as a `jsonb` array column rather than a separate versions table), `contract_exhibits` (a true single-parent child of `contracts` via `on delete cascade`, not polymorphic — `workspace_id` carried redundantly for RLS the same way `checklist_items`/`event_schedule_items` do, `document_id` a null placeholder for the future Media Library integration), widening the shared `notes`/`timeline_activities` tables' `owner_type` `CHECK` to add `'contract'` and `timeline_activities.type` `CHECK` to add the 10 Contract activity types, shared `updated_at` triggers on all three new tables, indexes (`workspace_id`+`status`, `client_id`, `event_id`, `template_id`, and a **workspace-scoped unique index on `contract_number`** — the durable duplicate-number guarantee), RLS enablement (Workspace isolation only via `is_workspace_member()` — `contracts` gets no delete policy, matching Leads/Clients/Events; `contract_templates` gets select-only, no write policy exists yet since the API has none; `contract_exhibits` gets a full select/insert/update/delete set, matching `checklist_items`), and the `generate_contract_number(uuid)` helper function

  - Dashboard Contract metrics (Total/Draft/Sent/Viewed/Signed/Pending Signature/Expired/Cancelled/Contract Value/Deposit Pending/Completed Value) required **no Dashboard code changes** — `getDashboardMetrics()` already computed `contractStats` from the repository-routed `getContracts({ includeArchived: true })` call, not a direct mock-store read, so it picked up live Supabase data automatically once the repository itself was routed.
  - 38 new tests (2 new files: the Contracts mock and Supabase repositories) covering Contract CRUD/filters/status+signature lifecycle/locked-edit rejection/contract-number uniqueness and collision-retry/duplicate independence/version-history accumulation/archive-restore, Exhibits CRUD/reorder/parent-validation, Templates listing, Notes/pin-unpin/Timeline, and Workspace-isolation/session-error handling; the existing migration-file-count assertion updated from 33 to 41.
