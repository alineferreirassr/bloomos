# BloomOS v1.0 — Launch Checklist

Operational steps a human operator must complete before/during go-live. This is distinct from `docs/v1.0-production-checklist.md` (the engineering readiness checklist, which is already fully checked off) — everything here is an external action outside this session's authority to perform (credentials, DNS, live third-party accounts), consistent with this engagement's standing rule to never guess, request, or enter credentials on the user's behalf.

## Environment & secrets

- [ ] Confirm `.env.local` (or the equivalent production env store) has `NEXT_PUBLIC_DATA_MODE=supabase` and a production (not staging) `NEXT_PUBLIC_SUPABASE_URL` + service-role key.
- [ ] Confirm every third-party credential referenced by the Integrations Platform is populated for the providers actually in use: Stripe, Google Calendar, Gmail, Twilio, DocuSign, Google Drive/Dropbox (see `docs/integration-security.md` for what's expected and how secrets are stored/redacted).
- [ ] Rotate any credential that was ever pasted into a chat, ticket, or non-vault location during development.

## Database

- [ ] Run every migration in `supabase/migrations/` against production, in order, via `npm run supabase:migration:up` (or the linked-project equivalent) — do not hand-apply SQL out of order.
- [ ] Confirm the seed migrations (`20260724101000_team_seed_data.sql`, `20260725100200_client_portal_permissions_seed.sql`, `20260803101000_finance_seed_chart_of_accounts.sql`, `20260808100000_analytics_permission_seed.sql`) ran successfully — these seed the `role_permissions` table and chart of accounts that mock mode substitutes for locally.
- [ ] Create the first real owner-role workspace member manually through Supabase Auth (sign-up flow or Admin API) — there is no seeded dev user in this codebase by design; do not create one with a guessed or shared password.

## Build & deploy

- [ ] `npm run build` succeeds in the production deploy environment (already verified in this session against the dev environment — confirm it also succeeds wherever the actual production build runs, since dependency resolution can differ).
- [ ] Confirm the production Next.js runtime target (the `middleware.ts`-to-`proxy.ts` migration warning surfaced during `next dev` — `docs/v1.0-known-limitations.md`/`v2-final-audit.md` do not track this as a blocker, but confirm the deployed Next.js version doesn't hard-fail on it).
- [ ] Confirm the production domain is set in whatever config drives Supabase Auth's redirect allowlist, so sign-in/magic-link/reset-password redirects land on the real domain, not `localhost`.

## Post-deploy smoke test (do this as a real signed-in user — this session could not, with no seeded credentials)

- [ ] Sign in as the first real workspace owner and confirm the dashboard loads.
- [ ] Walk one real record through the commercial pipeline: create a Lead, convert it, create an Event, generate a Proposal, accept it, create a Contract, create an Invoice, record a Payment — confirm each stage transition (verified at the code level in `docs/v2-final-audit.md`'s Checkpoint 45B Step 1 audit) behaves the same live as it does in the code trace.
- [ ] Confirm the Client Portal is reachable by a real client-invited account and shows the same record.
- [ ] Confirm at least one Workflow (e.g. the built-in "New Client Welcome" template) fires correctly against a real trigger.
- [ ] Check `/settings`, `/reports`, `/search`, `/workflows`, `/assets` each load without a permission-denied page for the owner role.

## Monitoring

- [ ] Point whatever error-tracking/APM tool the team uses at the production deployment (none is wired into this codebase by default — this is an infrastructure decision outside this codebase's scope).
- [ ] Confirm Supabase's own dashboard alerts (DB CPU, connection pool, auth failures) are enabled for the production project.

This checklist intentionally contains no code changes — every unchecked item above requires a human with production credentials to execute.
