# Portal Intelligence: Knowledge Graph, Executive Decisions, Analytics

Steps 14–16 — three thin translation seams over engines this checkpoint does not own. None of the three introduces a second graph, decision pipeline, or metrics engine.

## Knowledge Graph aggregation (Step 14)

Covered in full in [`client-portal-event-center.md`](client-portal-event-center.md) (`getClientPortalKnowledgeSummaryAction`) — the Event Center's own "How Everything Connects" panel is the sole surface this checkpoint gives the Knowledge Graph. `CLIENT_SAFE_NODE_TYPES` is the allowlist that keeps internal-only node types (comments, messages, reminders, workflows, template/clause library entities) from ever leaking through.

## Executive Decisions integration (Step 15)

`clientPortalRecommendationsForExecutiveDecisions()` (`modules/clientPortal/clientPortalExecutiveIntegration.ts`) is one more entry in the same `recommendationSources` list every other platform registers with (`contractRecommendationsForExecutiveDecisions`, `proposalRecommendationsForExecutiveDecisions`, etc.) — never a parallel decision pipeline. The only signal genuinely owned by the Client Portal — a client acting *through* it, not the internal team acting on their behalf — is a pending "Request Revision" on a Proposal (the Proposal Center's own Step 3 feature). `revision_requested_at` is real data the Proposal Platform's builder state already stores; this reads it back and, for every proposal with an unresolved revision request, translates it into an `OperationalRecommendation` via `clientPortalRevisionRequestToRecommendations()` (`core/clientPortal/clientPortalExecutiveIntegration.ts`) — never tracks a second copy of "did the client ask for changes."

## Portal Analytics (Step 16)

`modules/analytics/metrics/portalMetrics.ts` already registered 5 Portal-category metrics in Checkpoint 15, all counts over `ClientPortalActivityKind` entries from the Client Portal's own Activity log (`listClientPortalActivityForWorkspace`) — the single real source of "what a client did in their Portal session" this codebase has. This checkpoint adds the 3 remaining kinds that Checkpoint 15 hadn't yet given their own metric, generated by Centers this checkpoint built out:

| Metric id | Label | Activity kind |
|---|---|---|
| `portal.documentDownloads` | Document Downloads | `document_downloaded` (Document Center's download button) |
| `portal.invoiceViews` | Invoice Views | `invoice_viewed` (Billing Center) |
| `portal.messagesSent` | Messages Sent | `message_sent` (Communication Center's composer) |

`portal.documentViews` and Document Analytics' own `documents.views` deliberately read the same underlying Activity log entry — the checkpoint's own spec lists "Document views" under both dashboards, the same event framed two ways. Never a duplicated tracking mechanism, just two thin metric registrations over one source.
