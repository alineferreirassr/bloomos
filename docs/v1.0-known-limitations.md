# BloomOS v1.0 — Known Limitations

This document records every finding from the Checkpoint 45 Step 0 audit (see `docs/v2-final-audit.md`, Findings 7–23) that was investigated, confirmed real, and deliberately **not** fixed in this pass — with the reason it was deferred and a concrete path to close it. Nothing here was silently dropped: every item below was read in full, verified, and classified before the decision to defer it.

Governing principle for what's on this list: closing it would mean either (a) designing a new permission tier, (b) building new indexing/metric/wiring surface across several modules, or (c) cosmetic/performance polish — all closer to feature work than a bug fix, and out of scope for a checkpoint whose explicit instruction is "do not begin any new features."

---

## Security / permissions

### ~~No permission model for Executive Decisions / Objectives mutations~~ — Closed (Checkpoint 45A)
Fixed: `executive_decisions.manage` and `objectives.manage` added to `permission.ts`, assigned to the `manager` role (and inherited by `owner`/`admin`) in `permissionMatrix.ts`; checks wired into `updateDecisionStatusAction`, `createObjectiveAction`, and `updateObjectiveStatusAction`; 3 negative regression tests added. See `docs/v2-final-audit.md` Finding 14.

### Phase-1 MVP modules' permission strings are UI-only (Medium, documented intentional)
Leads/Clients/Events/Vendors/Purchases/Inventory/Services/Finance/Documents/basic-Contracts mutations run client-side with only Supabase RLS as server-side enforcement. `supabase/migrations/20260716100400_leads_rls.sql` explicitly documents this as workspace-isolation-only, no role gating, by design for this phase. The permission strings gating these modules' UI buttons give the appearance of granular RBAC without server-side enforcement of it.
**Why deferred:** already an explicit, documented product decision from an earlier phase — not a bug, but flagged here because the UI implies otherwise and it's worth a conscious go/no-go before calling this v1.0.
**Fix path:** either (a) accept as-is for v1.0 (workspace isolation is real; only role-level distinctions within a workspace are unenforced server-side), or (b) migrate these modules' mutations to Server Actions following the same pattern as every Checkpoint 27+ platform.

## Cross-platform integration gaps

### ~~Global Search omits `worker`/`team`/`equipment`/`vehicle`~~ — Closed (Checkpoint 45A)
Fixed: 4 fetcher functions added to `workspaceSearchProvider.ts`'s `CANDIDATE_FETCHERS`, plus registrations in `defaultRegistrations.ts`. See `docs/v2-final-audit.md` Finding 17.

### ~~Reporting Metric Registry omits Dispatch, Field Operations, Route Optimization, Operations Center~~ — Closed (Checkpoint 45A)
Fixed: `src/modules/reporting/metrics/operationsMetrics.ts` added, wired into `registerBuiltinReportMetrics.ts`. See `docs/v2-final-audit.md` Finding 18.

### Field Operations → Documents has no code path (Medium, found in Checkpoint 45B Step 1)
No code in `fieldOperationsActions.ts` references `documents`/`documentTemplates`, and the Merge Field Engine's registered domains have no field-operations/dispatch/execution-package coverage — a completed field session cannot feed into a generated document, even manually, because the merge-field data for it was never registered.
**Why deferred:** closing it means designing a new merge-field domain — feature work, not a bug fix.
**Fix path:** register a `field_operations`/`execution_package` merge-field domain in `registerMergeFields.ts`, following the existing per-domain pattern, and add it to `getGenerateDocumentPickerData.ts`'s picker options.

### Business Health engine's 9 dimensions predate Checkpoints 27–32 (Medium, found in Checkpoint 45B Step 1)
`computeBusinessHealthScore`'s 9 fixed dimensions (finance/crm/operations/inventory/team/events/payments/customerSatisfaction/risk) and `getExecutiveDashboardData.ts`'s data fetch never absorbed the 5 newer operational platforms (dispatch, execution packages, field operations, client journey, operational plans).
**Why deferred:** Executive Decisions (17 `*RecommendationsForExecutiveDecisions` providers) already provides a real, up-to-date cross-platform rollup covering all of these — this is not a missing-signal blocker, just a caveat that Business Health's own score specifically is stale relative to the newer platforms.
**Fix path:** either add dimensions for the 5 newer platforms to `computeBusinessHealthScore`, or explicitly document Business Health as commercial-pipeline-scoped and point users to Executive Decisions for full-platform health.

### Workflow Action Registry thin coverage; Notification Engine not directly wired from operational platforms (Medium, systemic)
Only `createDispatchAction` (batch-creation only) and the legacy Finance-level `createInvoiceAction` exist as Workflow Actions among the 8 newest operational platforms — 6 have zero. Separately, none of the 8 newest platforms (or the 4 comparison platforms checked) call `createInAppNotification` directly; every one relies on the generic `timeline_event` → user-configured-Workflow bridge (a deliberate Checkpoint 39 design) instead.
**Why deferred:** registering new Workflow Actions is additive feature surface, not a bug fix; the Notification gap is architecturally mitigated (not solved) by the Timeline bridge, so it doesn't block v1.0, just limits out-of-the-box notification behavior until a user configures a Workflow.
**Fix path:** register one Workflow Action per platform's most common mutation (e.g. `createFieldOperationAction`, `createProposalVersionAction`), following `createDispatchAction`'s existing pattern.

## Architecture / dead code (verified, not deleted)

Seven fully-implemented, authenticated, untested, zero-production-caller Server Action files were found via exhaustive per-export grep (not filename heuristics):
- `src/modules/integrations/manageOAuthConnectionActions.ts` (auth gap on its one exported function fixed in this pass — see `docs/v2-final-audit.md` Finding 8 — but the file's other 4 functions remain uncalled from production)
- `src/modules/integrations/twilio/connectTwilioActions.ts`
- `src/modules/integrations/docusign/setDocuSignWebhookSecretAction.ts`
- `src/modules/communication/presence/presenceActions.ts`
- `src/modules/communication/escalation/getEscalationsData.ts`
- `src/modules/communication/entityIntelligence/getEntityIntelligenceData.ts`
- `src/modules/ai/dailyBrief/getLatestDailyBriefExecution.ts`

**Why deferred:** every deletion must be justified per this checkpoint's own governing principle, and some of these may be staged infrastructure for near-term UI work rather than abandoned code (the same ambiguity as `core/ai/registry.ts`'s `registerAIProvider()`, which has test-only callers but a live sibling read path). Deleting working, tested-adjacent code without explicit confirmation risks destroying in-progress work.
**Fix path:** confirm with the user file-by-file whether each is staged-but-unwired or genuinely abandoned before removing.

Also verified and classified **Already-intentional, not duplication**: the `workspaceHealthEngine.ts` naming collision (`core/workspace/` vs `core/knowledge/`) and 6 other basename collisions across `src/core` — all read in full, all genuinely different logic/types/consumers. A naming-hygiene note, not a merge candidate.

12 circular dependencies (6 sibling module pairs: Contracts/Documents/Events/Expenses/Invoices/Payments `XListView.tsx` ↔ `XListCards.tsx`/`XListTable.tsx`) are all the same type-only import cycle — erased at compile time, `tsc`/build both pass clean, no runtime risk. Cosmetic/structural note only, not fixed.

Three more cosmetic items found during Checkpoint 45B's end-to-end lifecycle audit: a stale comment in `contracts/mockRepository.ts:431` claiming "no Invoice/Payments module exists yet" (both exist and are wired); an unused Timeline enum constant `welcome_sent_internally` with zero call sites; `field_operation` is not a registered `EntityType`/Knowledge Graph node type, unlike its siblings `dispatch_order`/`operational_plan`/`execution_package`. None affect behavior — comment/enum-hygiene and a minor KG-coverage gap only.

## Design / routing consistency (verified, not fixed — cosmetic, not functional)

- **Breadcrumbs**: 40 of 84 `PageHeader` breadcrumb usages are concentrated entirely in Checkpoint-27+ platforms; the original CRM/Finance/Documents/Vendors/Inventory/Purchases modules have zero.
- **Loading states**: the same newer-platform cohort mixes a bare `<p>Loading…</p>` with the shared `<Skeleton>` component the older modules use consistently, and mixes `EmptyState`/`ErrorState` interchangeably for the identical "record not found" case.
- **Typography**: 474 arbitrary `text-[Npx]` overrides across 174 files form a de facto shadow typography scale (`text-[17px]` alone ~150+ occurrences), matching neither Tailwind's default scale nor the Luxury dashboard shell's own named token scale.
- **Duplicate overlay primitives**: `LuxuryMobileNavigation.tsx`, `LuxuryClientMobileNavigation.tsx`, and `CopilotPanel.tsx` each hand-roll a full-screen overlay instead of composing the shared `Drawer` component.
- **`/finance-assistant` route** has zero nav/command-palette/internal-link entry points — fully built backend, no discoverable entry point.
- **`src/lib/middleware/routeProtection.ts`'s `PROTECTED_ROUTE_PREFIXES`** is stale (documented as "kept in sync manually," lists only 16 of ~46 route prefixes). Not a real auth gap — `src/app/(app)/layout.tsx` still authenticates every route server-side regardless — but unauthenticated visitors to the missing ~29 prefixes skip the fast middleware redirect and lose the post-login `redirectTo` param.

**Fix path for all of the above:** a dedicated design-consistency pass (Checkpoint 45 Step 4, or a future checkpoint) applying `PageHeader`'s existing `breadcrumb` prop, `Skeleton`, and `ErrorState` uniformly to the older-cohort modules; standardizing on the design-token scale; composing `Drawer` in the three hand-rolled overlays; adding a nav/palette entry for `/finance-assistant`; regenerating `PROTECTED_ROUTE_PREFIXES` from the same route list `routeAccess.ts` already maintains.

## Performance (verified, real; two closed in Checkpoint 45A, two remain — polish, not a blocker)

### ~~Un-debounced search inputs trigger a full server refetch on every keystroke~~ — Closed (Checkpoint 45A)
Fixed: shared `useDebouncedValue()` hook (`src/lib/useDebouncedValue.ts`) applied to all 9 affected list views (Clients, Contracts, Leads, Invoices/Expenses/Payments, Vendors, Inventory, Documents). See `docs/v2-final-audit.md` Finding 22.

### ~~Analytics dashboard recomputes the same base-table reads ~15-20x per page view~~ — Closed for the within-request case (Checkpoint 45A)
Fixed: `MetricComputeContext.cachedFetch` (populated by `computeVisibleMetrics()` with a per-call cache) + `resolveCachedFetch()` fallback in `core/analytics/engine.ts`; wired into `revenueMetrics.ts`/`clientMetrics.ts`. See `docs/v2-final-audit.md` Finding 23a.
**Still open:** the Executive Summary "Generate Summary" button calls `computeVisibleMetrics()` independently of the dashboard's own earlier call — a cross-request duplication a per-call cache can't fix. **Fix path:** pass the dashboard's already-computed snapshots into the AI Context Orchestrator, or add a cross-request cache with an explicit staleness policy.

### ~~CopilotPanel/CommandPalette eagerly bundled into every route~~ — Closed (Checkpoint 45A)
Fixed: `src/components/providers/DeferredFloatingWidgets.tsx` (a new `"use client"` wrapper, since the `(app)` layout itself is an async Server Component and can't call `next/dynamic(..., {ssr:false})` directly) code-splits CopilotPanel/CopilotLauncher/CommandPalette out of the initial route bundle. See `docs/v2-final-audit.md` Finding 23b.
**Note:** verified via `tsc`/`eslint`/`npm run build`/unit tests, not independently browser-verified — no seeded dev-mode credentials exist to sign in and confirm the panel/palette still open correctly at runtime.
