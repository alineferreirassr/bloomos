# v2.0 Checkpoint 8 — Finance Assistant (Financial Intelligence Engine)

Checkpoint 7 delivered the CRM Assistant, Bloom AI's first full business assistant. This checkpoint delivers its second — a **Finance Assistant** that behaves like a financial analyst for the Workspace, not a calculator and not a chatbot: current revenue, outstanding balances, upcoming cash flow, financial risk, and revenue opportunities, synthesized from BloomOS's own live Invoices, Payments, Contracts, Events, and Proposal history, plus this Workspace's own approved AI Memory and, when available, the CRM Assistant's own client-risk view.

**Non-goals, explicitly**: no Document Assistant, no Workflow Builder, no Automation Engine, no payment processing, no accounting exports, no tax calculations, no bank integrations. See `docs/finance-assistant.md`'s "Future extensions" for what's prepared but deliberately not implemented.

## Architecture

`Finance Assistant UI → executeSkill() → Finance Assistant Skill → Finance Context Builder → Memory Manager → Knowledge Store → Context Orchestrator → AI Runtime → Structured Output`, exactly as specified. `finance-assistant` (Step 1) is registered as a Skill with **no special execution path** — its `execute` is the same one-line `runSkillCompletion` delegation Proposal Generator, Event Operations Brief, Daily Operations Brief, Browse AI Memory, and CRM Assistant already use, this time against a new composite context (`financeAssistantContext`) plus two optional enrichments (`memory`, `crmAssistantContext`).

## Skill integration

`registerFinanceAssistantSkill.ts` proves the same "one Skill, zero special-casing" guarantee every prior checkpoint's own migration proved: `requiredPermissions: ["finance.view"]` (the primary permission, not every underlying data permission — the same precedent `daily-operations-brief`/`crm-assistant` established), `requiredContext: ["financeAssistantContext"]`, `optionalContext: ["memory", "crmAssistantContext"]`, `commandPaletteVisible: true`. The pre-existing `finance-assistant` **placeholder** (`registerUpcomingSkills.ts`, Coming Soon since Checkpoint 4) was removed and replaced by this real registration. `getBloomAIOverview.ts` needed exactly one new registration call to make Finance Assistant appear as the platform's sixth Active Skill (only Document Assistant remains Coming Soon), with Skill Statistics/Prompt Versions/the Skill Picker all updating automatically — zero Finance-Assistant-specific Dashboard code.

Unlike CRM Assistant, Finance Assistant does **not** get its own sidebar entry: the existing "Finance" nav module is a direct link (`/finance`), not an expandable group, and converting it into one purely to slot in a second link would have been a larger, more disruptive UX change than this checkpoint's scope calls for (confirmed by a failing `Sidebar.test.tsx` assertion when this was tried and reverted — see "Known limitations"). Finance Assistant stays fully discoverable via the Bloom AI Dashboard, the "Ask Bloom" picker, and its own direct URL (`/finance-assistant`) — the same three paths Daily Brief and Browse AI Memory already rely on without a dedicated sidebar entry.

## Memory usage

The Skill declares `optionalContext: ["memory", "crmAssistantContext"]` — both requested, neither required. `memoryContextBuilder.ts` (Checkpoint 6) already filters to `approvalStatus: "approved"` only, so **"never expose rejected memories" is satisfied at the source**. `registerFinanceAssistantUseCase.ts`'s `composeContext` merges the optional `memory` section into `context.recentMemories` (threaded into the model's own prompt and surfaced in the report's "Recent AI Insights" section) and the optional `crmAssistantContext` section into `context.crmRecommendations` — reusing CRM Assistant's own already-computed `clientsAtRisk` rather than re-detecting client risk a second time. **This is the first time one Skill's own composite context section is itself consumed, optionally, by a different Skill**, proving the Context Orchestrator's sections compose across Skills, not just within one. Three dedicated tests in `generateFinanceAssistantBrief.test.ts` prove: an approved memory surfaces, a still-`"proposed"` one never does, a `"rejected"` one never does, and a real CRM Assistant client-risk entry (fetched via a mocked `fetchCrmAssistantMaterials`) correctly reaches `brief.crmRecommendations`.

## Validation

`financeAssistantModelOutputSchema` (Zod) mirrors every prior checkpoint's own bounded-length, closed-shape guarantee. `semanticValidation.ts` mirrors Daily Brief/CRM Assistant/Proposal Generator's **hard-reject** precedent: every `financialRiskExplanations[].riskId` must already be on the deterministic risk list computed by `contextBuilder.ts`'s own `computeFinancialRisks` (an escalation over Payment Delays: an Invoice overdue beyond 14 days, or an unsigned Contract whose Event is imminent or past); every action's `targetId` is cross-checked against real ids present in context for its `targetType` (`invoice`/`contract`/`event`). This is architectural prevention, not detection — the model has no free-text field through which it could name a fabricated Payment, amount, Contract, Client, Event, or balance at all, satisfying Step 5's "never hallucinate financial data" by construction. 9 dedicated semantic-validation tests plus 9 schema tests cover every rejection and acceptance path.

`Payment`'s own type doc comment already confirms BloomOS never stores card numbers or bank details; per this checkpoint's own "never expose sensitive payment credentials" instruction, `FinanceAssistantPaymentSummary` stays conservative anyway — a closed projection that excludes `reference`, `payment_method`, and `notes`, carrying only what a financial summary actually needs.

## Date-determinism fix (quality improvement before certification)

Before certifying this checkpoint, the full suite was re-run and two assertions in `generateDailyOperationsBrief.test.ts` (Checkpoint 5) failed — a pre-existing, unrelated bug the passage of a real calendar day exposed: `"Invoice INV-1 overdue by 25 day(s)"` had drifted to `26` because the test never controlled "what time is it right now," only the Invoice's own fixed `due_date`. Per this checkpoint's own explicit direction, the fix targeted the **underlying source of nondeterminism**, not the failing assertions:

- **`core/time/clock.ts`** (new) — one function, `clockNow(): Date`, the single seam every "what time is it right now" default should call instead of `new Date()` directly. A test can freeze the entire call graph's notion of "now" with one `vi.mock("@/core/time/clock", () => ({ clockNow: vi.fn(() => FIXED_DATE) }))`, without threading a `now` parameter through every intermediate layer between a Server Action and the pure function several layers down that actually needs it.
- Applied to every `now: Date = new Date()` default this class of bug could reach: `dailyBrief/contextBuilder.ts`, `dailyBrief/assembleBrief.ts`, `dailyBrief/notifications.ts` (the three Daily Brief functions that compute a relative day-count), and — proactively, before they could exhibit the identical bug — `crmAssistant/contextBuilder.ts`, `financeAssistant/contextBuilder.ts`, and the shared `modules/finance/financialSummary.ts` (`computeWorkspaceFinancialSummary`'s own `referenceDate` default), since all three are this checkpoint's and Checkpoint 7's own newly-built code following the exact same pattern.
- `generateDailyOperationsBrief.test.ts` now mocks `@/core/time/clock` to a fixed instant (`2026-07-26T12:00:00.000Z`, the date the test's own fixtures were originally authored against) — its "N day(s) overdue" assertions are now permanently deterministic regardless of which real calendar day the suite runs on.
- A dedicated `core/time/clock.test.ts` covers the one real behavior worth testing (returns a live `Date` by default).
- A repo-wide grep confirmed no other test in the suite exhibits the same pattern (a hardcoded date fixture combined with a live, unmocked day-count computation) — every other `daysUntilEvent`/`daysOverdue`-adjacent match found was a plain literal test fixture, not a live computation, and therefore never at risk of drifting.
- Explicitly avoided: patching the failing assertions' expected numbers (would have made the suite pass today and fail again on the next calendar-day rollover) and `vi.useFakeTimers()` faking the global clock wholesale (risked interacting badly with `setTimeout`-based provider-timeout logic elsewhere in the same call graph) — the Clock-abstraction-via-module approach avoids both.

## Known limitations

- **No Finance Assistant sidebar entry.** Deliberately not added — the existing "Finance" nav module is a direct link, not an expandable group like "CRM"; converting it purely to slot in a second link was tried, found to break an existing `Sidebar.test.tsx` assertion (duplicate "Finance" text once nested), and reverted as a larger, more disruptive UX change than this checkpoint's own scope calls for. Fully discoverable via the Bloom AI Dashboard, Ask Bloom, and its own direct URL instead.
- **The "Ask Bloom" picker's generic fallback route** (pre-existing platform behavior, not introduced this checkpoint) — picking "Finance Assistant" from a page with no registered runner falls back to `/bloom-ai`, not directly to `/finance-assistant`. Same limitation already flagged for CRM Assistant in Checkpoint 7's own report.
- **Proposal history, Daily Brief history, and Activity are always mock-only**, even in a real Supabase-backed Workspace — confirmed unchanged from Checkpoint 7's own audit.
- **No dedicated `finance.*` AI permission** — reuses `finance.view`, the same "primary permission" precedent every other workspace-wide Skill already follows.
- **No production AI provider is registered** — the Finance Assistant, like every other Skill, runs against its own deterministic mock, clearly labelled throughout the UI.

## Recommendation

**APPROVED.** The Finance Assistant executes entirely through `executeSkill()` with no special execution path, delivering all 12 spec'd output sections on a dedicated `/finance-assistant` page, hard semantic validation against three entity types, memory integration that both informs the model's narrative and surfaces informationally (never exposing a rejected or still-proposed memory), and the first working example of one Skill optionally consuming another Skill's own context section. Verified live against a real Supabase-backed Workspace on both desktop and mobile, with figures cross-checked against `/dashboard`'s own independently-computed Finance metrics. Before certification, a pre-existing, unrelated date-nondeterminism bug in Checkpoint 5's own test suite was found and fixed at its root cause (a new, reusable `core/time/clock.ts` Clock abstraction), rather than patched at the symptom — the full suite is now fully deterministic regardless of which calendar day it runs on. Per the stop condition, Document Assistant, Workflow Builder, and Automation Engine have not been started; no further feature work begins on any of them without further direction.
