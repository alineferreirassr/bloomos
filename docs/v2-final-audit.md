## Methodology

Five `Explore` sub-agents were run in parallel against the full repository, each scoped to one audit category:

1. **Architecture & duplication** — logic/UI/engine/store/module-action/Timeline-event/Knowledge-Graph-relationship/permission/route duplication across all 45 checkpoints.
2. **Dead code & orphans** — unused providers, unreachable/deprecated code, stale TODOs, orphaned types/interfaces/routes/permissions/Timeline types/entity types/relationship types/workflow nodes/notification channels.
3. **Security & permissions** — every mutating Server Action, checked for session gating, permission checks, and tenant/workspace ownership validation on every entity id accepted as input.
4. **Routes, navigation & design system** — route-guard coverage, permission-gating consistency, design-token/pattern consistency.
5. **Cross-platform data integrity** — merge/compile/generation pipelines that cross module boundaries (documents, contracts, invoices, proposals) for cross-tenant leakage.

Agent 3 and Agent 5 returned Critical/High severity findings. Per explicit instruction, this document was created and all findings below were classified **before** any further code change beyond the fixes already required to close the Critical/High items. A follow-up investigation (documented under Finding 4 below) was run specifically to determine whether a suspected pattern in Agent 3's report was an isolated bug or systemic — this surfaced a much larger scope issue that is flagged for a go/no-go decision rather than fixed unilaterally.

## Severity taxonomy

| Severity | Definition |
|---|---|
| **Critical** | Exploitable cross-tenant data exposure or data corruption with no auth barrier. |
| **High** | Missing authorization (permission or ownership) on a state-mutating action reachable by any authenticated member. |
| **Medium** | Missing authorization on a lower-risk mutation, or a security-adjacent gap with partial mitigation elsewhere. |
| **Low** | Defense-in-depth gaps (error-message leakage, missing input validation) with no direct exploit path found. |
| **Known intentional exception** | Explicitly disclosed in code/comments as a deliberate, scoped decision from a prior checkpoint. |
| **False positive** | Investigated and found not to be a real issue. |

## Findings

### Finding 1 — [CRITICAL] Cross-tenant data leak in the Merge Field Engine

**Component:** `src/core/documents/compiler.ts` (`compileTemplate()`), reachable from both the manual document-generation path (`src/modules/documentTemplates/compileDocumentAction.ts`) and the Workflow-automation path (`src/modules/documentTemplates/generateDocumentAction.ts`).

**Root cause:** `MergeContext` (`types/documentPlatform.ts`) accepts arbitrary entity ids (`clientId`, `leadId`, `eventId`, `invoiceId`, `contractId`, `proposalId`, `vendorId`) to resolve merge-field values for a document. The compiler fetched and merged these records by id without ever verifying the fetched record's `workspace_id` matched the calling session's workspace. A caller who could influence any of these ids (e.g. a compromised/misconfigured Workflow automation, or a caller with a mistyped/malicious id) could pull another workspace's client/lead/event/invoice/contract/vendor/proposal data into a generated document.

**Fix applied:** Added `validateMergeContextOwnership(context: MergeContext)` inside `compiler.ts` itself — the single choke point every document-generation path already passes through. It fetches each provided entity by id and confirms `record.workspace_id === context.workspaceId` before merge-field substitution proceeds; any mismatch (including "record doesn't exist at all") returns the same generic `permission_denied` `DocumentIssue`, so the two failure modes are indistinguishable to a caller (no existence-oracle). `automationId`/`automationExecutionId` were confirmed exempt — `workflowMergeFields.ts` only regex-parses these, never fetches a record with them.

**Files changed:**
- `src/core/documents/compiler.ts` — new `validateMergeContextOwnership()`, wired into `compileTemplate()`'s issue collection.
- `src/core/documents/compiler.test.ts` — 9 new tests: positive (all ids owned), negative (no ids), 5 cross-tenant regressions (one per entity type + a combined case), missing-id-treated-as-cross-tenant, and a dedicated test asserting the error message never discloses existence.
- Regression fixes (fabricated test ids needed real stubs once the check went live): `src/core/documents/manager.test.ts`, `src/modules/documentTemplates/getDocumentHealthAction.test.ts`, `src/modules/documentTemplates/getDocumentAnalyticsAction.test.ts`.

**Tests:** `npx vitest run src/core/documents src/modules/documentTemplates` — 23 files / 204 tests passed.

**Status:** ✅ Fixed and verified. No caller of `compileTemplate()` bypasses this — confirmed by reading both call sites.

### Finding 2 — [HIGH] Workspace-isolation gap in Client Journey information requests

**Component:** `src/modules/clientJourney/clientJourneyActions.ts` — `setInformationRequestStatusAction` and `respondToInformationRequestAction`.

**Root cause:** Both actions accepted a raw `id` and mutated the corresponding `ClientInformationRequest` (via `setStatus()` / `recordClientResponse()`) after only checking that the session was active — never confirming the request belonged to the session's workspace. A member of workspace A could change the status of, or respond on behalf of, a client information request belonging to workspace B, as long as they had (or guessed) the record's id.

**Fix applied:** New `loadOwnedInformationRequest(id, workspaceId)` helper — fetches via the existing `getCoreClientInformationRequestsService().getRequestById(id)` and returns `null` if the record doesn't exist or its `workspaceId` doesn't match. Both actions now call this immediately after the session-active check and return the existing generic `NOT_FOUND_ERROR` on a mismatch — identical to the not-found case, no existence-oracle.

**Files changed:**
- `src/modules/clientJourney/clientJourneyActions.ts`
- `src/modules/clientJourney/clientJourneyActions.test.ts` — new `describe("cross-tenant workspace isolation", ...)` block: 3 tests (both actions rejected for a cross-tenant id with record-untouched verification; both rejected identically for a nonexistent id).

**Tests:** 20/20 tests passed in this file.

**Status:** ✅ Fixed and verified.

### Finding 3 — [MEDIUM] 7 Contract Platform mutations with no permission check

**Component:** `src/modules/contractPlatform/contractPlatformActions.ts` — `createCustomContractTemplateAction`, `createCustomClauseAction`, `createContractVersionAction`, `publishContractVersionAction`, `archiveContractDocumentAction`, `restoreContractVersionAction`, `markContractReadyAction`.

**Root cause:** All 7 actions checked only `session.kind === "active"`, never `session.permissions.includes(...)`. The corresponding permission strings (`contract_templates.manage`, `contract_clauses.manage`, `contract_versions.manage`, `contract_builder.manage`) already existed in `src/core/enums/permission.ts`, with their intended scope for these exact actions documented inline (Checkpoint 34 comment, lines 245–268) — the permissions were designed but never wired in. Any active member, regardless of role, could create/publish/archive/restore contract templates, clauses, and versions.

**Fix applied:** Wired the pre-existing, pre-documented permission strings into each action — no new permission strings invented, per explicit instruction:
- `createCustomContractTemplateAction` → `contract_templates.manage`
- `createCustomClauseAction` → `contract_clauses.manage`
- `createContractVersionAction`, `restoreContractVersionAction` → `contract_versions.manage`
- `publishContractVersionAction`, `archiveContractDocumentAction`, `markContractReadyAction` → `contract_builder.manage`

**Files changed:**
- `src/modules/contractPlatform/contractPlatformActions.ts`
- `src/modules/contractPlatform/contractPlatformActions.test.ts` — session fixture extended with `contract_versions.manage`; new `describe("permission enforcement (v2 Checkpoint 45 security fix)", ...)` block, 7 negative tests (one per fixed action, verifying rejection with zero permissions).
- `src/modules/clientPortal/getClientPortalContract.test.ts` — regression fix, `memberSession.permissions` extended with `contract_versions.manage` (this file calls `createContractVersionAction` for real).

**Tests:** `npx vitest run src/modules/contractPlatform src/modules/clientPortal src/modules/contracts` — 47 files / 258 tests passed, including the 7 new negative tests.

**Status:** ✅ Fixed and verified.

### Finding 4 — [HIGH, systemic — ✅ FIXED, all 12 platforms] The same "documented but never wired" permission gap exists across every operational platform built since Checkpoint 27

**Discovery:** After fixing Finding 3, a follow-up investigation was run to check whether the same pattern (a `.manage` permission that exists in `permission.ts`/`permissionMatrix.ts` and is *documented* in `routeAccess.ts` as covering a platform's mutations, but is never actually `.includes()`-checked inside that platform's own action file) exists elsewhere. It does — extensively.

`src/core/permissions/routeAccess.ts` carries the **identical disclaimer comment template** — *"`X.manage` exists in `permissionMatrix.ts` for future UI-level gating, never checked inline in `xActions.ts` itself"* — for essentially every platform added from Checkpoint 27 onward, including `contractPlatformActions.ts` (the platform just confirmed to be a genuine bug in Finding 3, not an intentional design). Because the exact same disclaimer covered a confirmed bug, **the disclaimer cannot be trusted as evidence of intentional design for any of the other platforms it also covers.**

Per the explicit instruction governing this phase ("no broad refactors while Critical/High findings remain open" and "do not declare production-ready while any Critical/High finding remains open"), this is being surfaced for a go/no-go scope decision rather than actioned immediately.
