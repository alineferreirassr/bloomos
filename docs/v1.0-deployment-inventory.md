### 11. Site / redirect / callback / webhook / OAuth URLs

- **Site origin**: derived dynamically per-request from the `host` header (`getSiteOrigin()` in `src/lib/auth/actions.ts`) — not hardcoded, so no env var or code change is needed for this specifically. Falls back to `http://localhost:3000` only if the `host` header is literally absent (never happens behind Vercel/any real proxy).
- **Auth callback route**: `/auth/callback` (`src/app/auth/callback/route.ts`) — used for password-reset and any Supabase magic-link flow. Built dynamically as `${origin}/auth/callback?next=/update-password`.
- **Internal `redirectTo` query param**: used by `/sign-in`, `/invitations/[token]`, `/client-invitations/[token]` — same-origin only, validated by `safeRedirectTarget()` to reject any absolute or protocol-relative URL (defense against open-redirect).

- **OAuth `redirect_uri`**: built by `oauthEngine.ts`/`oauthTokenExchange.ts` from the connecting workspace's own request context, not hardcoded.

## 21. Authentication configuration required

- Supabase Auth email/password sign-in is the only auth method this codebase uses (`signInWithPassword`/`signUpWithPassword`/`resetPasswordForEmail` in `src/lib/auth/actions.ts`) — no OAuth/social sign-in for BloomOS's own login.
- **Supabase Dashboard → Authentication → URL Configuration** must be set for the production domain before deploying: Site URL = the production domain, and the Redirect URLs allowlist must include `https://<production-domain>/auth/callback` (used by the password-reset flow). This is an external dashboard setting, not a code change — nothing in this codebase can perform it.
- No seeded dev/demo user account exists anywhere in this codebase or its migrations — the first real user must be created through Supabase Auth directly (sign-up, or the Supabase Admin API) once deployed. This engagement's own memory/notes have consistently flagged this: no dev credentials were ever available to browser-test the authenticated app.
- **Blocker, not yet fixed** (found during this audit, not previously documented in `docs/v2-final-audit.md`/`docs/v1.0-known-limitations.md`): `src/core/integrations/credentialManager.ts`'s `EncryptionProvider` seam only has one implementation, `InMemoryEncryptionProvider` — explicitly self-documented as "not actually encrypt[ing]," storing values in a plain in-process `Map`. This is fine for local dev/testing, but is a **hard blocker for connecting any real external integration in a deployed environment**: (a) Vercel's serverless functions don't share memory across invocations or instances, so a secret "encrypted" on one invocation would be unreadable on the next; (b) even on a persistent server, an in-memory `Map` provides no actual encryption at rest. This is precisely why the instruction to not connect Stripe/Gmail/Twilio/DocuSign/Drive/Dropbox yet is the right call — connecting any of them today would either crash (secret unreadable after the storing invocation exits) or, if it somehow persisted, store the raw secret in a way indistinguishable from plaintext. **Fix path** (not performed): implement a real `EncryptionProvider` backed by a KMS/Vault (or Supabase's `pgsodium`/Vault extension) and call `setEncryptionProvider()` with it before any real integration is connected.
